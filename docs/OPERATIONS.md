# CMhelper 운영 정책 (Operations Policy)

본 문서는 CMhelper B2B SaaS 플랫폼의 장애 등급별 관리 정책 및 고객 공지, 보안 유지보수 정책을 정의합니다. (실제 실행 절차는 `RUNBOOK.md` 참고)

## 1. 장애 등급 및 대응 정책

### P1 (Critical) - 전체 서비스 중단
*카카오톡 업데이트로 인한 전체 발송 불가, 메인 DB 서버 다운 등*
- **대응 정책:** 신규 발송 즉시 중지 (예약 큐 프리징). 모든 가용 인력을 투입하여 원인 파악.
- **고객 보호:** 1차적으로 안정성이 확보된 이전 버전 에이전트 롤백 검토.
- **고객 공지:** 발생 즉시(1시간 이내) 원인, 영향 범위, 복구 예상 시간을 포함한 [장애 긴급 공지] 템플릿 발송.

### P2 (High) - 핵심 기능 장애 / 일부 고객 장애
*특정 환경(OS/해상도)에서 발송 실패 다발, 파일 첨부 기능 오류 등*
- **대응 정책:** 영향받는 기능 격리(안내 팝업 등) 및 실패 작업(Retry Queue / Failed Queue) 데이터 보존 최우선.
- **Fallback:** pywinauto 실패 시 OpenCV 등 2차 Fallback 모드 강제 활성화 검토.
- **고객 공지:** 에이전트 팝업 또는 웹 대시보드 배너를 통한 지연 공지.

### P3 (Medium) - 일부 비핵심 기능 오류
*특정 커스텀 필드 노출 오류, 일부 UI/UX 오작동*
- **대응 정책:** 임시 우회 절차(Workaround)를 고객에게 제공하고 다음 정기 패치(핫픽스)에 반영.
- **고객 공지:** FAQ 또는 공지사항 게시판 업데이트.

### P4 (Low) - 단순 UI/UX 문제 및 버그
*오타, 단순 정렬 깨짐 등 동작에 지장 없는 이슈*
- **대응 정책:** 정상 운영 유지. 제품 백로그(Product Backlog)에 등록 후 다음 마이너 릴리즈 시 일괄 수정.

## 2. Third-party Dependency 유지보수 정책 (카카오톡)

- **Remote Config (중앙 관리):** 카카오 데스크톱 UI 식별자 변경에 대비해 서버 중앙 배포(Remote Config) 시스템을 유지한다. (설계 단계)
- **Canary Test (사전 감지):** 매일 오전 6시 가상(Test) 계정 기반의 자동 발송 파이프라인을 구동하여 카카오 잠수함 패치를 조기 감지한다. (설계 단계)
- **Auto Update:** 장애 패치 시 영업사원의 수동 개입을 없애기 위해 Agent 자동 업데이트 런처 체계를 유지한다. (설계 단계)
